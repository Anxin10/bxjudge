# Beyblade X 本地裁判 Agent — 設計文件

日期：2026-10-21
狀態：已確認（2026-10-21）

## 1. 目的與動機

使用者在 Google 雲端硬碟存有大量 Beyblade X 比賽影片（例如 2026-10-01 一個晚上就有 50 支以上，每支 86 MB–1 GB，手機以固定支架拍攝整個戰鬥盤）。人工逐支看影片判斷發射有沒有失誤、誰贏、怎麼贏，非常耗時。

目標是在使用者自己的電腦（RTX 3090 24 GB VRAM、32 GB RAM、Windows 11）上建立一套**本地 AI 裁判 Agent**：

1. 自動看完每支影片，逐回合判斷**發射檢查**與**勝負結果**。
2. 依照日本 Takara Tomy 官方 Beyblade X 規則計分。
3. 拿不準的回合標記出來交給人工覆核，不默默給出錯誤結果。

分工：本地 Agent 負責實際判斷；Claude（透過 Claude Code）負責設計、調整判定規則與門檻，並根據人工覆核的修正紀錄持續優化。

## 2. 名詞與畫面約定

- **X side**：畫面**左方**的選手。
- **B side**：畫面**右方**的選手。
- **下盤戰鬥區（戰鬥區）**：盤底陀螺能正常跑的區域（不含 Over Zone、Xtreme Zone 口袋）。「落入戰鬥區」指落進這裡。
- **上盤（蓋子）**：蓋在戰鬥盤上方的透明蓋子。陀螺落在蓋子上不算落入戰鬥區；發射器碰到蓋子也算碰到戰鬥盤。
- **擊飛區域**：即 Over Zone。**極限區域**：即 Xtreme Zone。
- **Over Zone**：盤面下部左右兩端的口袋。
- **Xtreme Zone**：盤面下部中央的口袋（有 Xtreme 軌道的那一側）。
- **回合（round）**：一次雙方同時發射到分出結果。一場比賽（match）由多個回合組成，先到 4 分者勝。

## 3. 範圍

### 目標（要做）

- **發射檢查**（每回合、每一方各判一次）
  - **觸碰盤面**：發射瞬間，手或發射器有沒有碰到戰鬥盤。**唯一判斷依據是「手或發射器碰到盤面所造成的晃動」**；陀螺落地衝擊、陀螺碰撞、旁人碰到桌子等其他原因造成的晃動都不算（見 6.4）。
  - **落入戰鬥區**：陀螺離開發射器後，有沒有落進戰鬥區。
  - **空判（空碰）**：兩顆陀螺**都還沒落入戰鬥區時**就在空中互相碰撞（每回合判一次，不分方別）。
- **勝負結果**（每回合）
  - 哪一方得分（X side / B side），以及終結方式與分數：
    - Spin Finish 1 分：對手先停止旋轉。
    - Over Finish 2 分：對手進入 Over Zone。
    - Burst Finish 2 分：對手陀螺解體（Bit 脫落、Ratchet 脫離等）。
    - Xtreme Finish 3 分：對手進入 Xtreme Zone。
- 依回合累計比分，判斷整場（先到 4 分）勝者。
- 每個判定附**信心分數**與**證據時間點**，低信心者標記「需覆核」。
- 人工覆核介面，覆核結果回存，用於再訓練與調整門檻。

### 非目標（這版不做）

- **不使用聲音**：影片不一定有音軌。因此**不判斷搶拍**（未依「3、2、1、Go Shoot」口令發射）。
- 不做比賽現場即時判定，只處理錄好的影片（離線批次）。
- 不辨識陀螺的型號、零件組合。
- 不辨識選手身分（只區分 X side / B side）。
- 不取代正式裁判；輸出是輔助紀錄與覆核工具。

### 反目標（即使技術上能跑，出現就算失敗）

- 判定錯誤卻沒有標成「需覆核」（高信心的錯判）。
- 規則寫死在程式碼裡，官方改版或換比賽就要改程式。
- 修改或刪除雲端硬碟上的原始影片。
- 需要把影片上傳到任何雲端 AI 服務（必須全本地）。裁判系統本身凡是能在本地執行的部分（模型、標註、覆核、VLM）一律本地執行（使用者再次確認）。

## 4. 已知限制

| 限制 | 對設計的影響 |
|---|---|
| **主要處理已拍好的影片**（如 10/1 這批），**鏡頭拍法不會改**（使用者確認） | 系統必須在現有拍法下運作，不能靠「改鏡頭」解決問題 |
| 鏡頭固定在盤面**前方低角度斜拍**，不是正上方俯拍 | 盤面有透視變形，區域要用多邊形標，不能假設圓形；Xtreme Zone 靠近鏡頭，看得清楚 |
| 畫面中**看不到選手的手** | 觸碰盤面只能靠盤面晃動判斷，不做手部偵測 |
| 影片不一定有聲音 | 完全不依賴音軌 |
| 每次拍攝的鏡頭位置可能略有不同 | 每個「拍攝設定」要做一次校準（見 6.2） |
| 推測**一支影片 ≈ 一個回合**、約 4K 60fps（由檔名時間間隔與檔案大小換算，位元率一致約 90 Mbps，每支約 10–90 秒） | 回合切分仍要支援一支多回合，但以一支一回合為主要情況；推論前必須降解析度 |
| 影片在 Google 雲端硬碟，電腦上目前沒有同步 | 在 WSL 內用 rclone 唯讀同步比賽資料夾（見 5）；Agent 只讀不寫 |
| 手機錄影可能是 HEVC (H.265) 編碼 | 用 ffmpeg 搭配 NVIDIA 硬體解碼 |
| 官方規則的發射失誤罰則未明確寫出 | 罰則做成設定檔選項（見 7） |

## 5. 硬體與軟體選擇

### 執行環境（使用者指定：WSL）

- **WSL2**（使用者已安裝，shell 為 zsh）。所有程式、模型、標註工具、覆核介面都在 WSL 內執行；Windows 端只用瀏覽器開 `localhost` 頁面。
- GPU：RTX 3090 24 GB，NVIDIA 驅動 595.97，WSL 內可用 CUDA 13.2（`nvidia-smi`、`nvcc 13.2` 已確認）。桌面平常佔用約 2.8 GB VRAM，實際可用約 21 GB。
- PyTorch：使用目前**最新穩定版**，搭配 CUDA 13.x 的官方 wheel（cu130 或 cu132，以實作當時 pytorch.org 安裝頁的穩定選項為準）。PyTorch wheel 自帶 CUDA runtime，不依賴系統的 nvcc。RTX 3090（Ampere, sm_86）仍在 CUDA 13 支援範圍內。
- Python：WSL 內獨立環境（版本依 PyTorch 與 SAM 3 需求，SAM 3 需要 Python 3.12）。
- **影片取得**：在 WSL 內用 **rclone**（Google Drive 唯讀權限）把比賽資料夾同步到 WSL 自己的檔案系統（例如 `~/bx/videos`），不要直接讀 `/mnt/c`、`/mnt/g`（跨系統讀取大檔案很慢）。rclone 第一次需要使用者自己在瀏覽器授權 Google 帳號。一批約 50 支影片約需 15–20 GB 空間。
- 影片解碼：ffmpeg，優先使用 NVDEC 硬體解碼（WSL 下需實測可用；不可用時改 CPU 解碼）。

### 模型選擇（使用者要求：最新、訓練快又好；以下為 2026-10 查詢結果，Claude 的決定）

| 用途 | 主要選擇 | 理由 | 備案 |
|---|---|---|---|
| **自動預標註** | **SAM 3.1**（Meta，2026-03） | 輸入文字（例如「spinning top」）就能找出並在整段影片中追蹤所有目標，大幅減少使用者標註時間；用它產生的框當預標，使用者只修正 | Grounding DINO 類的零樣本偵測 |
| **陀螺偵測（自訓練）** | **RF-DETR**（Roboflow，Apache 2.0） | 2026 年即時偵測準確度領先（COCO：RF-DETR-M 54.7 mAP / 4.4 ms，高於 YOLO26m 的 53.1 / 4.7 ms），且**在少量自訂資料上微調表現特別好**，符合 300–500 張標註的規模 | **YOLO26**（Ultralytics 最新版，AGPL，個人使用沒問題）：最小型號更快、訓練工具最成熟 |
| **追蹤** | ByteTrack（`supervision` 套件） | 與 RF-DETR / YOLO26 都能搭配 | BoT-SORT |
| **疑難覆核 VLM** | **qwen3.8:27b**（Ollama，約 18 GB） | Ollama 上最新的 Qwen 模型，原生支援圖片與影片理解 | **qwen3-vl:8b**（約 6.2 GB）：較快，VRAM 不足或速度太慢時使用 |

- **偵測模型的決定方式**：RF-DETR 與 YOLO26 用**同一份標註**各訓練一次（各約 1–2 小時），以使用者覆核過的回合當測試集，比較準確率與速度後選定。小物體與動態模糊的表現，公開數據無法定論，必須用自己的影片比。
- 盤面晃動偵測：OpenCV（特徵點比對 / ECC 影像對齊），不需要深度學習模型。
- 標註工具：Label Studio（WSL 內執行，Windows 瀏覽器開啟）。
- 覆核介面：本地網頁（Streamlit 或同等工具）。

### VRAM 分配

各階段**依序執行，不同時佔用**：

| 階段 | 約略 VRAM |
|---|---|
| SAM 3.1 預標註 | 4–10 GB（依影片長度，需實測） |
| RF-DETR / YOLO26 訓練 | 8–14 GB |
| 偵測 + 追蹤推論 | 2–4 GB |
| qwen3.8:27b 覆核 | 約 18–20 GB（推論前卸載偵測模型） |

21 GB 可用的情況下，qwen3.8:27b 只能單獨執行；若與其他程式衝突，改用 qwen3-vl:8b。

## 6. 處理流程

```
雲端硬碟同步資料夾
  → [6.1 建立清單]
  → [6.2 鏡頭校準]
  → [6.3 解碼與回合切分]
  → [6.4 發射檢查]  ┐
  → [6.5 結果判定]  ┘→ [7 規則引擎計分] → [8 低信心交給 VLM] → [9 人工覆核] → 輸出
                                                                   ↓
                                                         [10 修正紀錄回饋優化]
```

### 6.1 建立清單

掃描同步資料夾，為每支影片記錄：檔名、雲端硬碟檔案 ID（若可取得）、長度、fps、解析度、編碼、有無音軌、拍攝日期時間（由檔名 `YYYYMMDD_HHMMSS` 解析）。已處理過的影片以檔案大小 + 修改時間判斷，不重複處理。

### 6.2 鏡頭校準

- 每個「拍攝設定」（同一天、同一支架位置）做一次。
- 使用者在一張代表畫面上點選並存成 JSON：
  - 場地：盤面外框多邊形（含蓋子；用於晃動偵測的參考區域）
  - 上盤：蓋子多邊形
  - 下盤戰鬥區多邊形
  - 擊飛區域：左、右 Over Zone 多邊形
  - 極限區域：Xtreme Zone 多邊形
  - X side（左）/ B side（右）的發射區域（盤面上方左右兩半）
- 新影片自動與既有校準畫面比對相似度；相似就沿用，差太多就要求重新校準。

### 6.3 解碼與回合切分

- 解碼後降到推論用解析度（例如長邊 1280），保留原始 fps 以捕捉快速事件。
- **回合開始**：盤內從「沒有旋轉中的陀螺」變成「出現陀螺」的時間點（即發射）。
- **回合結束**：判定出終結事件後，或盤內所有陀螺都靜止 / 被拿出。
- 一支影片切出 0 個以上的回合；切不出回合的影片標記「需覆核」。

### 6.4 發射檢查

**發射時間窗**：從偵測到第一顆陀螺進入畫面的前 0.5 秒，到兩顆陀螺都落入戰鬥區後 0.5 秒（數值為初始值，之後調整）。

**觸碰盤面（只算手或發射器造成的晃動）**
- 以 6.2 的盤面外框區域做參考，逐格計算盤面相對於參考畫面的位移（像素）。
- 只在發射時間窗內檢查；比賽進行中的晃動**不算**。
- 晃動要**排除其他原因**，才能判定為觸碰。三個條件都成立 → 判定「有觸碰」：
  1. 盤面位移超過門檻；
  2. 晃動開始的時間點，**沒有**同時發生陀螺落地（6.4 落地時間點）、陀螺撞盤壁、陀螺互撞（±3 格內）；
  3. 晃動開始時，該側的發射器（或入鏡的手）位於盤緣附近，或正在往盤面方向移動。
- **發射器只認本體**（使用者要求）：拉繩式發射器的棉線、拉條式發射器的拉條都**不算**發射器。條件 3 只看發射器本體是否靠近盤緣；拉繩或拉條碰到盤面不算觸碰。
- 只符合條件 1，但條件 2 或 3 無法確認（例如發射器沒入鏡）→ 標「晃動原因不明，需覆核」，**不直接判觸碰**。
- 發射器本體有入鏡、但晃動時不在盤緣附近 → 判「無觸碰」，附註「晃動非發射器本體造成」（可能是拉繩、拉條或其他原因），覆核時可查看。
- 晃動與陀螺落地等事件同時發生 → 判定為陀螺造成，不算觸碰，但在覆核介面附註，讓覆核者可以查看。
- **歸屬哪一方**：依條件 3 中靠近盤緣的是哪一側的發射器。無法判斷歸屬時，標「觸碰，方別不明，需覆核」。
- 門檻初始值由 10/1 影片中人工確認的「正常發射」、「觸碰發射」、「陀螺落地造成的晃動」三類樣本統計得出。

**落入戰鬥區**
- 追蹤每一方的陀螺從出現到落地的路徑。
- 在時間窗內，陀螺的位置進入戰鬥區多邊形並持續一段時間 → 成功。
- 陀螺沒有進入、掉出盤外、卡在盤緣、**停在上盤蓋子上** → 判定該方「未落入戰鬥區」。
- 斜拍時蓋子在畫面上會與下盤戰鬥區後半部重疊。陀螺停穩的位置若同時落在兩者的範圍內，以下盤戰鬥區為準；若只在蓋子範圍內停穩，判定為落在蓋子上。
- **「落地」不能只看 2D 位置**：低角度斜拍時，空中的陀螺投影到畫面上也可能落在戰鬥區多邊形內。落地時間點要同時符合：位置在戰鬥區內，且垂直方向的快速移動結束、轉為沿盤面的平順移動（軌跡轉折點）。

**空判（空碰）**
- 在**兩顆陀螺都尚未落地**的期間（以上面的落地時間點為準），檢查兩者是否碰撞。
- 只看畫面重疊不夠（斜拍時前後重疊不代表碰到），碰撞要同時符合：
  - 兩顆陀螺的偵測框接觸或重疊；
  - 同一時間（±2 格）兩者的軌跡都**突然改變方向或速度**。
- 只符合其中一項 → 標「可能空碰，需覆核」。
- 4K 60fps 原始畫面在這段時間窗內**不降幀**，以免漏掉瞬間碰撞（推論解析度仍可降低）。

### 6.5 結果判定

- **方別歸屬**：陀螺在發射時位於左側 → X side；右側 → B side，之後靠追蹤 ID 延續。追蹤中斷後重新接上的情況，信心降低。
- **Xtreme Finish**：某方陀螺的最終位置在 Xtreme Zone 多邊形內 → 對方得 3 分。
- **Over Finish**：某方陀螺的最終位置在 Over Zone 內 → 對方得 2 分。
- **Burst Finish**：某方陀螺的追蹤目標分裂成多個零件偵測，或出現零件偵測而原陀螺消失 → 對方得 2 分。
- **Spin Finish**：雙方都在戰鬥區內，某方先**轉停** → 對方得 1 分。**轉停 = 靜止，或旋轉方向反轉**（使用者要求）：
  - 靜止：陀螺外觀在連續格之間幾乎不變，且位置不動。
  - 反轉：陀螺裁切畫面內的旋轉方向（光流）與發射時的方向相反，且持續數格。
  - **混疊防護**：陀螺剛發射時每秒轉數十到上百圈，遠高於 60fps，畫面上看到的旋轉方向是假的（車輪效應）；減速過程中轉速每次經過每秒 60 圈、30 圈附近也會「看起來反轉」。所以**只有在陀螺幾乎不再移動、畫面上旋轉已很慢時**看到的反轉才算轉停，之前的反轉一律忽略。
  - 轉停原因（靜止或反轉）記在判定理由中，方便覆核。

### 6.6 發射後旋轉方向 flag（使用者要求）

- 每回合為雙方各記一個旋轉方向 flag：`x_spin_dir` / `b_spin_dir`，值為 `right`（右旋）、`left`（左旋）、`unknown`。
- **不直接看陀螺本身的轉向**（發射後轉速遠高於影格率，會混疊），改量陀螺落地後前 2 秒在盤內**繞行的方向**（順時針 / 逆時針，相對於戰鬥區中心），再依設定檔的對應表換算成右旋 / 左旋。
- 對應表（繞行方向 → 右旋 / 左旋）放在設定檔，**驗收時用已知右旋 / 左旋的陀螺影片確認**。
- 繞行不足半圈或方向來回不定 → `unknown`。
- 反轉判定（6.5）以此 flag 作為「原本的方向」；flag 為 `unknown` 時，只用影片中轉速變慢後最先穩定看到的方向作為基準。
- **同時發生**、**雙方都出局**、**無法判斷**等情況，交給規則引擎依設定處理（見 7），並標記需覆核。

### 偵測模型的類別

| 類別 | 用途 |
|---|---|
| `bey` | 完整的陀螺 |
| `bey_part` | Burst 後散落的零件 |
| `launcher` | 發射器**本體**（判斷發射時間、方別與觸碰；只在入鏡時可用）。**標註時框只框本體，不含拉繩的棉線、不含拉條** |

訓練資料：從 10/1 影片抽格，由使用者標註 300–500 張起步；先用 SAM 3.1 以文字提示自動預標並在影片中追蹤，使用者只需修正。抽格要涵蓋發射瞬間、激烈碰撞、Burst、進入各口袋、靜止等各種狀況，不能只抽平均間隔的畫面。

## 7. 規則引擎（設定檔）

規則全部寫在 YAML 設定檔，不寫死在程式中。初始內容依目前查到的官方資訊：

```yaml
rules_version: "takara-tomy-bx-regulation-v12-2026-03"   # 已核對官方第 12 版（見下）
win_points: 4
finish_points:
  spin: 1
  burst: 2
  over: 2
  xtreme: 3
launch_check:
  stadium_touch: redo          # 發射時接觸 → 重新對戰（2025 世界大會作法）
  bey_not_in_battle_area: redo # 陀螺落到盤外、卡在盤緣或停在蓋子上 → 重新對戰
  mid_air_collision: redo      # 空判（空碰）→ 重新對戰（官方第 12 版一致）
  repeat_miss_penalty: none    # 選項：none / opponent_1pt_on_2nd_miss（各比賽判法不同）
draw:                           # 雙方同時停止、同時出局等
  action: redo
```

規則來源（2026-10-21 查詢）：
- 計分、4 分制、發射接觸與落到盤外重來：HOBBY Watch 對 2025 世界大會的報導。
- 官方規定只寫「發射失誤由裁判提醒」，罰則由現場工作人員判斷：玩家整理的大會注意事項。
- 2026-10 已取得並逐項核對官方規則 PDF 第 12 版（2026 年 3 月，2026-03-13 施行，SHA256
  `c0950dba…26541`），`config/rules.yaml` 與 README「規則核對」記錄來源、與官方一致的項目、
  使用者自訂項目（只算發射器本體觸碰、預設不額外罰重複失誤）與已知限制（Barrel Griffon
  分離 barrel）。選用的 `opponent_1pt_on_2nd_miss` 依官方計數（得分或罰分清除雙方失誤數，
  雙方同時第 2 次失誤無效）。

## 8. 視覺語言模型覆核

- 模型：qwen3.8:27b（備案 qwen3-vl:8b），見 5。
- 只處理信心分數低於門檻的判定（初始門檻 0.7）。
- 輸入：事件前後各 1 秒的關鍵畫面（約 6–10 張）+ 校準區域標示 + 結構化問題（例如「左方陀螺最後停在哪個區域？」）。
- 輸出：JSON（答案、理由）。**VLM 的答案不會覆蓋主要判定**，只作為覆核時的參考資訊。

## 9. 輸出與人工覆核

### 每回合的輸出欄位

| 欄位 | 說明 |
|---|---|
| `video`, `round` | 影片檔名、第幾回合 |

| `vlm_note` | VLM 的意見（如有） |

輸出成 CSV + JSON，另有每場比賽的比分彙總。`rounds.csv` 另加 `x_land_zone`、`b_land_zone`（發射後第一個停穩的區域）。

### 陀螺軌跡紀錄（使用者要求）

- 每回合輸出一份軌跡檔（CSV）：每一格、每一方（X / B）的陀螺位置、所在區域（下盤戰鬥區、上盤蓋子、左 / 右 Over、Xtreme、盤上其他、盤外）、偵測信心；Burst 零件另列。
- 每回合輸出一張軌跡圖：在校準畫面上畫出 X（藍）與 B（紅）的路徑，標出落地點、空碰點、終結點。
- 覆核介面顯示軌跡圖；軌跡檔保留供日後分析（例如各陀螺常落在哪一區、被擊飛的方向）。

### 覆核介面

- 列出所有回合，可依「需覆核」篩選。
- 每回合顯示發射瞬間與結束瞬間的截圖、區域標示，點一下跳到影片該時間點播放。
- 覆核者可確認或修改各欄位，修改內容存檔。

## 10. 持續優化（Claude 的角色）

- 人工修正紀錄存成結構化檔案（哪支影片、哪個回合、原判定、正確答案）。
- Claude 讀取修正紀錄，分析錯誤類型，調整：晃動門檻、時間窗長度、區域多邊形、信心門檻、規則設定；必要時建議補標註、再訓練 YOLO。
- 每次調整後以已覆核的回合作為測試集重跑，比較準確率，確認沒有變差才採用。

## 11. 成功標準（初始值，Claude 的決定）

在 10/1 這批影片上：
- 未標記需覆核的回合中，終結方式與得分方的正確率 ≥ 95%。
- 人工確認的發射觸碰，≥ 90% 有被判出或標記需覆核。
- 人工確認的空判（空碰），≥ 90% 有被判出或標記需覆核。
- 需覆核的回合比例 ≤ 30%，並隨優化逐步降低。
- 一支 5 分鐘以內的影片，處理時間 ≤ 影片長度。
