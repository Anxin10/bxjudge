# E1c：以觀察到的放手時間修剪回合起點（2026-11-25）

> **結論：** E1c 的實作正確，也有方向性的效果，但**只修剪到 3 局**。在驗證集上仍然**產出 0 個判決**。單獨開啟幾乎沒有作用；和 E1b 一起開時，18、19 號從沒有身份變成全程正確指派。**不建議部署**，下一步要先做 E1d。
>
> **另外發現：** 我標的 AI 真值中，12、18、19 號的 X/B 命名反了，已經在使用者同意後修正並重算。13 號經確認沒有標反。詳見 §5。

## 1. 設計

| 項目 | 內容 |
|---|---|
| 開關 | `config/identity.yaml` 的 `release_clock_trim_enabled`，**預設 `false`**，必須是布林值（嚴格載入） |
| 函式 | `launch_phase.trim_rounds_to_release(rounds, releases, pre_frames)` |
| 接入點 | `pipeline.py`，在 `segment_rounds` 之後、軌跡重建之前 |
| 規則 | 回合內如果有**觀察到的發射器放手**（`prepare_launch_tracks` 的 `phase.releases`），起點改成「最早的放手 − `launch_pre_s`」。**更正：** 實際執行時 `config/physical_time.yaml` 會把它覆寫成 62.5 ms（120 FPS 下約 8 幀），不是 `thresholds.yaml` 的 0.5 秒 |
| 不做的事 | 沒有放手的回合不改；起點只會往後、不會往前；不推測放手時間；不指派 X/B |
| 稽核 | 被修剪的回合記在 geometry json 的 `identity.release_clock_trim`（原始區間與新起點） |

**為什麼用 `phase.releases`：** 在驗證集上，`phase.releases` 觀察到的 6 次放手時間都正確。native 軌跡的 mount→separated 則會在準備階段產生假的放手（例如 12 號的 native 2 在 4.88 秒）。

## 6. 結論與下一步

1. **E1c 的方向正確：** 只要觀察到放手，回合起點就能對準（誤差 < 0.1 秒），並且和 E1b 一起解除 18、19 的身份問題，其中 18 的缺場地幾何也一起解除。
2. **但適用範圍太小**（3/14 局），因為大部分回合**根本沒觀察到放手**。真正的瓶頸是放手偵測率，不是修剪規則。
3. **E4 的停轉判定仍會選到被手拿走的勝方**（19、201410），必須加上「手進場後的消失不算停轉」之類的防護。
4. **建議：**
   - 不部署。開關保持預設關閉。
   - **E1d**：在沒有觀察到放手時，用「著地」作為回合時鐘；同時確認 `round_release_evidence` 在修剪後還找得到上膛片段。
   - AI 真值的 X/B 命名已修正（§5.1）。12–21 的終局時間和勝負仍然只有 AI 標註，最好再由人工抽查。
